## Track A. Design and execute one synthetic increment

1. After recorded activation, the Lead Orchestrator may commission a bounded design. Reconcile SFCI-6 through SFCI-11 prospectively and reuse an existing issue where appropriate. Remove P0 dependencies only for separable work within the accepted scope. Use one issue for the first increment and record design acceptance and execution dispatch separately. The proposed design path is `docs/technical-design/P1/SF-CI-TDD-P1-LEX-001.md`.
2. Before implementation, require independent review and accountable acceptance of the exact design and any applicable ADR, verification of the approved development and CI environments, and an effective bounded product execution grant. The approved plan must enumerate exact implementation paths within `mix.exs`, `lib/sf_codeintel/`, `test/` including dedicated synthetic fixtures, `README.md` and `.github/workflows/ci.yml`. The grant must bind the environment, root, actor, allowed commands and writes, resource and retry limits, cleanup and STOP conditions.
3. Use a trusted read-only local source adapter behind a narrow product-owned interface. Allow one explicitly approved synthetic root per session. Use standard libraries and existing trusted tools where practical. Support bounded source retrieval, reliable module and function discovery, source-grounded definition lookup, lexical reference candidates and freshness checks. Return source spans and freshness evidence for supported results. Label lexical references as candidates and report unsupported or unresolved results explicitly. Exclude a duplicate graph engine, compiler, language server and unqualified backend integration.
4. Verify the increment through actual Elixir service launch, MCP initialization, tool discovery and calls from an authorized client. Check exact fixture bytes and source ranges, module and function discovery, definition lookup, candidate labels, retrieval bounds, unsupported and ambiguous results, edit/rename/delete freshness, path escape denial and basic CLI diagnostics. Require observed passing product CI on the exact hosted head. Mock-only results and optional `Proof` do not establish this milestone.

Use the existing approved development environment only if its controls suffice for the grant. Scope is limited to project-owned development and read-only synthetic source inspection. This amendment grants no target-code execution, acquisition or execution of unqualified upstream backend code, private or unrelated repository access, unapproved network acquisition, new privileged operations, spending increase, production adoption, release or deployment. Apply the existing containment and authorization requirements.
